CAPÍTULO 4. DISEÑO E IMPLEMENTACIÓN DE LA APLICACIÓN (MVC, SEGURIDAD Y FLUJO)
================================================================================

4.1 Contexto y objetivo del sistema
El sistema “Registro y Control de Bienes de la Aldea Universitaria” fue construido en PHP puro, con arquitectura MVC (Model–View–Controller), permitiendo administrar el ciclo de vida de los bienes (altas, modificación y bajas) y controlar el acceso mediante autenticación por roles.

Objetivos funcionales implementados:
- Login de usuarios con verificación segura de contraseña.
- Autorización por roles (admin y operador).
- CRUD de bienes: listar, registrar, editar y eliminar.
- Dashboard con estadísticas simples sobre los bienes.
- Preparación de base de datos usando SQLite vía migración, para posteriormente migrar a MySQL en XAMPP.

================================================================================
4.2 Arquitectura MVC
================================================================================

4.2.1 Punto de entrada y enrutamiento (public/index.php + Router)
El archivo `public/index.php` actúa como punto de entrada único.

Su flujo general es:
1) Inicia sesión: `session_start()`.
2) Carga el autoload/base por medio de `app/bootstrap.php`.
3) Instancia y ejecuta el router principal `App\Core\Router`.

`App\Core\Router`:
- Toma la ruta desde `$_SERVER['REQUEST_URI']`.
- Elimina barras y normaliza la URL.
- Divide la URL por “/” para obtener: controlador y acción.
- Construye el nombre de clase del controlador siguiendo un patrón:
  - controlador: `/bienes` → `BienesController`
  - acción: por defecto `index` cuando no se especifica.
- Verifica existencia de la clase y del método.
- Si no existe, responde 404 usando vista `app/Views/layouts/404.php`.

Notas técnicas:
- El router implementa un mapeo simple por convención, reduciendo configuración manual.

================================================================================
4.3 Capa Controller
================================================================================

Los controladores coordinan la lógica de aplicación por request:
- Autenticación: antes de ejecutar operaciones sensibles.
- Validación de datos (para creación/actualización).
- Validación CSRF en métodos POST.
- Llamado a modelos (persistencia).
- Renderizado de vistas con datos.
- Mensajes “flash” para feedback al usuario.

Controladores presentes y su rol:
1) `app/Controllers/AuthController.php`
   - `login()` muestra formulario con token CSRF.
   - `doLogin()` valida CSRF, extrae credenciales, autentica con `Auth::login()` y redirige.
   - `logout()` cierra sesión.

2) `app/Controllers/BienesController.php`
   - `index()` lista bienes y permite filtrar por `estado` (vía GET).
   - `create()` muestra formulario de alta con CSRF.
   - `store()` procesa alta:
     * valida CSRF
     * valida reglas (required/string/max/in/unique)
     * inserta con `Bien::create()`
     * redirige con flash.
   - `edit()` muestra formulario de edición (valida existencia del bien).
   - `update()` actualiza bien:
     * valida CSRF
     * valida reglas
     * ajusta la regla `unique` cuando el código cambia
     * ejecuta `Bien::update()`.
   - `delete()` elimina bien:
     * valida CSRF
     * ejecuta `Bien::delete()`.

3) `app/Controllers/DashboardController.php`
   - `index()` requiere login y calcula estadísticas:
     * total de bienes
     * agrupación por estado
   - Renderiza `app/Views/dashboard/index.php`.

4.4 Capa Model
================================================================================

4.4.1 Modelo Bien (CRUD)
`app/Models/Bien.php` implementa métodos:
- `all(?string $estado)`
  - Construye una consulta con filtro opcional por `estado`.
  - Ejecuta consulta con prepared statement.
- `find(int $id)`
  - Busca un bien por ID.
- `create(array $data)`
  - Inserta con parámetros nombrados.
- `update(int $id, array $data)`
  - Actualiza por ID.
- `delete(int $id)`
  - Elimina por ID.

4.4.2 Modelo User
`app/Models/User.php` se utiliza en el login para:
- buscar el usuario por email (`findByEmail`) y leer `password_hash`.

================================================================================
4.5 Capa Core (seguridad y utilidades)
================================================================================

4.5.1 Conexión a base de datos mediante PDO (SQLite/MySQL futuro)
`app/Core/Database.php` centraliza la conexión.

Funcionamiento:
- Usa un patrón “singleton” para mantener una única instancia PDO.
- Selecciona driver desde `config.php`:
  - SQLite: `sqlite:<ruta>`
  - (extensible) MySQL: `mysql:host=...;dbname=...;charset=utf8mb4`

Opciones de PDO configuradas:
- `PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION`
  - ante errores, se lanzan excepciones.
- `PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC`
  - fetch como arrays asociativos.
- `PDO::ATTR_EMULATE_PREPARES => false`
  - prepared statements reales (evita emulación insegura).

Además:
- para SQLite, `ensureParentDir()` crea el directorio de la base si no existe.

4.5.2 Autenticación y roles
`app/Core/Auth.php` gestiona sesión y autorización.

Componentes:
- `user()` / `check()` / `role()`
  - leen la información del usuario desde `$_SESSION['user']`.
- `requireLogin()`
  - si no hay sesión, redirige a `/auth/login`.
- `requireRole($role)`
  - si el rol no coincide, responde HTTP 403.
- `login($email, $password)`
  - busca usuario por email.
  - verifica contraseña con `password_verify()` contra `password_hash`.
  - si es correcto, guarda datos del usuario en sesión.
- `logout()`
  - limpia `$_SESSION`, borra cookie de sesión (si aplica) y destruye sesión.

4.5.3 Protección CSRF
`app/Core/Csrf.php` protege formularios sensibles.

Funcionamiento:
- `token($formId)`:
  - genera un token aleatorio si no existe.
  - lo guarda en `$_SESSION['csrf_tokens'][$formId]`.
- `validate($formId, $token)`:
  - verifica token usando `hash_equals` (comparación segura en tiempo).
- `regenerate($formId)`:
  - rota el token luego de un POST exitoso.

Uso en formularios:
- Login: token asociado a `login`.
- Bienes:
  - alta: `bien_create`
  - edición: `bien_edit`
  - eliminación: `bien_delete`

4.5.4 Filtrado de XSS en vistas
Las vistas imprimen datos dinámicos usando `htmlspecialchars(..., ENT_QUOTES, 'UTF-8')`.

Ejemplo:
- En `app/Views/bienes/index.php`, campos como `nombre`, `codigo`, `ubicacion`, `estado`, `responsable` se muestran escapados.

Esto evita que un atacante inyecte HTML/JS que el navegador interpretaría.

================================================================================
4.6 Validación de datos
================================================================================

El controlador usa `app/Core/Validator.php` (presente en el proyecto) para aplicar reglas como:
- `required`
- `string`
- `max:<n>`
- `in:<valores>`
- `unique:<tabla>:<campo>`

En `BienesController`:
- `store()` valida campos antes de insertar.
- `update()` valida y ajusta la unicidad cuando el código se modifica.

CAPÍTULO 5. IMPLEMENTACIÓN DETALLADA DE MÓDULOS (CRUD, DASHBOARD, LOGIN)
================================================================================

5.1 Módulo de autenticación (Login/Logout)

5.1.1 Render de login (GET /auth/login)
Controlador: `AuthController::login()`

Flujo:
- Si el usuario ya está logueado (`Auth::check()`), redirige a `/dashboard`.
- Si no, renderiza vista `app/Views/auth/login.php`.
- La vista genera y embebe el token CSRF con `Csrf::token('login')`.

5.1.2 Procesamiento de login (POST /auth/doLogin)
Controlador: `AuthController::doLogin()`

Flujo de seguridad:
1) Lee `csrf_token` desde POST.
2) Valida CSRF: si falla, retorna HTTP 419 y termina.
3) Extrae `email` y `password`.
4) Llama `Auth::login()`:
   - busca usuario por email
   - valida contraseña con `password_verify`
5) Si falla, registra mensaje flash y redirige a login.
6) Si es correcto, guarda sesión y redirige a `/dashboard`.

5.1.3 Logout
Controlador: `AuthController::logout()`
- ejecuta `Auth::logout()`
- muestra flash informativo
- redirige a `/auth/login`.

================================================================================
5.2 Módulo CRUD de Bienes
================================================================================

5.2.1 Listar bienes (GET /bienes)
Controlador: `BienesController::index()`

Flujo:
- exige login
- obtiene `estado` opcional desde GET
- invoca `Bien::all($estado)`
- renderiza `app/Views/bienes/index.php`.

5.2.2 Crear bien (GET /bienes/create)
Controlador: `BienesController::create()`
- exige login
- renderiza formulario con token CSRF `bien_create`
- entrega valores iniciales vacíos al template.

5.2.3 Guardar bien (POST /bienes/store)
Controlador: `BienesController::store()`

Flujo:
- exige login
- valida CSRF con `Csrf::validate('bien_create', $token)`
- regenera token luego de validación
- construye `$data` desde POST y aplica `trim()`
- valida con reglas (incluye `unique` en `codigo`)
- si hay errores: flash warning y redirección al formulario
- si todo es válido: inserta con `Bien::create($data)` y redirige a lista.

5.2.4 Editar bien (GET /bienes/edit?id=...)
Controlador: `BienesController::edit()`
- exige login
- castea `id` a int
- carga bien con `Bien::find($id)`
- si no existe: responde 404
- si existe: renderiza vista de edición con CSRF `bien_edit`.

5.2.5 Actualizar bien (POST /bienes/update)
Controlador: `BienesController::update()`

Flujo:
- exige login
- valida CSRF `bien_edit`
- lee id y datos
- valida reglas
- ajusta condición de unicidad:
  - si el `codigo` cambió respecto al registro original, activa `unique`
- actualiza con `Bien::update`
- redirige con flash.

5.2.6 Eliminar bien (POST /bienes/delete)
Controlador: `BienesController::delete()`

Flujo:
- exige login
- lee id y token CSRF `bien_delete`
- valida token y regenera
- ejecuta `Bien::delete($id)`
- redirige a lista.
